# RK3588 部署调研：从相机通信到算法落地

> 调研日期：2026-11-15
> 目标：把当前的涂胶检测算法从工控机迁移到以 RK3588 为主控的传感器内部，形成"相机 + 计算 + 触发"一体化的产品形态（对应 `docs/product-development-roadmap.md` 的 P5/P6）。
> 说明：本文中的芯片参数取自瑞芯微官方页面，模型性能取自 RKNN Model Zoo 官方基准，其余为工程判断，已在文中标注"待确认"。

---

## 一、结论摘要

| 维度 | 结论 |
| --- | --- |
| 相机链路 | 有三条路：**USB3 直连**（最快验证）、**MIPI CSI-2 直连**（产品形态）、**GMSL2 远传**（长线/强干扰）。建议按 P5→P6 顺序推进 |
| 带宽 | 3 路 1280×960@30fps 原始灰度合计约 **111 MB/s**，USB3 与 MIPI 都能满足，千兆网接近打满 |
| 传统算法 | 移植成本低，但需针对 ARM 优化（当前 Python 实现 p95 136 ms，必须降到 33 ms 内） |
| 深度学习 | YOLO 系列可上 NPU（INT8 量化）；**RPN 的提案/ROI 层不适合 NPU**，需要拆分或改造 |
| 最大风险 | ① 海康 USB3 相机的 Linux 内核驱动能否在 RK3588 BSP 上编译；② 全局快门 MIPI 模组的供应与驱动；③ 密封环形结构内的散热 |

---

## 二、约束条件

来自论文与现有设计（见 `docs/reproduction-bom.md`、`docs/product-development-roadmap.md`）：

| 项目 | 要求 |
| --- | --- |
| 相机数量 | 3 台，互成 120° |
| 分辨率与帧率 | 1280×960，≥30 fps |
| 视野与精度 | 100×80 mm 视野，±1 mm 检测精度 |
| 触发 | 24 V 机器人 IO 硬件触发，三路同步 |
| 节拍 | 机器人涂胶速度 1.1 m/s，1 ms 时间差 ≈ 1.1 mm 位移 |
| 单帧耗时 | 论文反光分支约 80 ms；实时目标为 33 ms/帧 |
| 形态 | 环形传感器，外径约 150 mm、内孔 45/65 mm，密封 |

**关键判断**：1.1 m/s 下，如果三路相机不是同一硬件触发源，几毫秒的偏差就会变成几毫米的位置差，因此**必须硬件同步触发 + 全局快门**，这一条在选型时优先级最高。

---

## 三、相机通信链路对比

单路数据量：1280 × 960 × 1 B × 30 fps ≈ **36.9 MB/s**；三路合计 **110.6 MB/s**。

| 方案 | 物理层 | 可用带宽 | 3 路可行性 | 优点 | 缺点 | 适用阶段 |
| --- | --- | --- | --- | --- | --- | --- |
| USB3.0/3.1 | USB 3.x Gen1 5 Gbps | 约 400 MB/s 实测 | 可行，需独立控制器与供电 | 现有相机直接用；免改结构 | 线缆短、需 Hub、驱动依赖厂商 SDK；长时间多路易掉线 | P5 台架 |
| MIPI CSI-2 | D-PHY，4 lane | 每 lane 约 2.5 Gbps，4 lane ≈ 10 Gbps | 可行（RK3588 支持 4×4 lane） | 带宽大、体积小、板内走线、延迟低 | 走线长度受限（<30 cm）、需选型与驱动调试、无标准热插拔 | P6 产品 |
| GMSL2 | 同轴，3/6 Gbps | 3 Gbps ≈ 375 MB/s | 可行 | 线缆可达 10 m 以上、抗干扰、车规 | 需解串器（MAX9296 类）与转接板、成本高 | 长线/强干扰场景 |
| 千兆以太网 | 1000BASE-T | 约 118 MB/s | 三路接近打满，不建议 | 布线通用、距离远 | 带宽吃紧、延迟不确定 | 对外输出，不作为相机链路 |

**RK3588 原生接口**（瑞芯微官方参数）：

- 视频输入：32 MP ISP，支持 4×4 lane 或 4×2 lane + 2×4 lane 的 MIPI CSI-2，另支持 DVP 与 HDMI2.0 输入；
- 高速接口：PCIe 3.0/2.0、SATA3.0、RGMII、Type-C、USB3.1、USB2.0；
- NPU：6 TOPS，三核，支持 INT4/INT8/INT16/FP16/BF16/TF32；
- CPU：4×Cortex-A76 + 4×Cortex-A55（8 nm）。

结论：**MIPI 通道数量足够接 3 路相机**，USB3 也可行；GMSL 需要额外的解串板（已有第三方 RK3588 GMSL 转接套件）。

## 四、三条落地路线

### 路线 A：RK3588 + 现有 USB3 相机（P5 台架，最快验证）

```
3 × MV-CB013-20UM ──USB3──> 独立 USB3 控制器/Hub ──> RK3588 板
                                                        │
                                          MVS Linux (aarch64) 或自研 U3V
                                                        │
                                                  算法流水线
```

- **可行性依据**：海康机器人已发布 MVS V5.1.0 Linux（aarch64）客户端（2026-09 发布）；社区已有 Jetson（aarch64）上使用 MVS + OpenCV 的案例。
- **注意**：MV-CB013-20UM 走 **USB3 Vision（U3V）** 协议，不是 UVC，**不能**直接用 `cv2.VideoCapture` 打开，必须用 MVS SDK 或自写 U3V 驱动。
- **待确认**：MVS Linux 下 USB3 相机通常需要厂商提供的内核驱动模块（具体模块名以 SDK 安装说明为准），需针对 RK3588 厂商内核重新编译；不同 BSP 版本可能不兼容。
- **价值**：不改硬件即可验证"ARM 上能不能跑通整条链路"，是风险最低的第一步。

### 路线 B：MIPI CSI-2 + 自研载板（P6 产品形态）

```
3 × MIPI 模组 ──FPC──> RK3588 SoM ──> 载板（触发、供电、LED 驱动）
```

- **RK3588 支持 4×4 lane CSI**，三路相机可各占一组 4 lane，带宽充裕。
- **相机选型要点**：必须**全局快门**。可关注 OV9281（1 MP 黑白全局快门，1280×800，MIPI 接口有现成模组与上游驱动）或 AR0234（2.3 MP 全局快门）；普通卷帘模组（IMX415 等）不适合 1.1 m/s 运动拍摄。
- **风险**：模组供应、镜头接口（M12）、BSP 中 sensor 驱动与 ISP tuning；需要提前向模组厂确认 RK3588 适配情况。

### 路线 C：GMSL2 远传（可选，长线/强干扰）

- 适用：传感器与计算单元分离、线缆超过 1 m、电磁干扰强的工位。
- 需要 GMSL2 相机 + 解串板（如 MAX9296 方案）+ RK3588 转接套件，已有第三方套件可采购。
- 成本与功耗高于路线 B，建议作为备选。

## 五、采集与预处理管线（RK3588 侧）

RK3588 的媒体链路与 x86 不同，建议这样组织：

| 环节 | 方案 | 说明 |
| --- | --- | --- |
| 采集 | V4L2（MIPI）或厂商 SDK（USB3） | 尽量用 DMA-BUF 零拷贝，避免 memcpy |
| 裁剪/缩放/格式转换 | RGA（2D 加速） | 把 1280×960 缩放/裁剪交给硬件，CPU 只做算法 |
| 灰度化 | RGA 或 OpenCV（NEON） | OpenCV 需自行交叉编译并开启 NEON |
| 录像（可选） | MPP 硬编码 | 仅在需要留档视频时使用 |
| 算法 | CPU（A76）+ NPU | 传统 CV 在 CPU，深度学习在 NPU |

**性能提示**：当前 Python 版量测链路（BFS + 骨架直径）在合成图上 p95 已达 136 ms，直接搬到 A76 只会更慢。移植前必须做两件事：BFS 换 `cv2.connectedComponents`、骨架/形态学走 OpenCV 优化路径，必要时用 C++ 重写量测模块。

## 六、算法部署

### 6.1 传统 CV 部分（第 4 章）

- 纯 OpenCV + numpy 实现，移植成本低；
- 注意：aarch64 上需交叉编译 OpenCV（开 NEON），Python 版可保留用于离线分析，实时路径建议 C++；
- 标定参数（内参、映射表）以文件形式随设备出厂固化。

### 6.2 深度学习部分（第 3 章）

| 模块 | 部署方式 | 风险 |
| --- | --- | --- |
| B2 反光检测（YOLOv3-5FL + SPP） | 导出 ONNX → RKNN-Toolkit2 量化（INT8/FP16） | YOLOv3 不在官方 Model Zoo 示例中，需自行导出；SPP、上采样均为常规算子，可行性较高 |
| B1 RoI 定位（RPN） | backbone + 分类/回归头可上 NPU；**proposal/NMS 需放 CPU** | ROI Align、候选框生成不是 NPU 友好算子 |

**官方性能基准**（rknn_model_zoo，RK3588 单核、INT8、输入 640×640）：

| 模型 | 单核 FPS |
| --- | --- |
| YOLOv5n | 84.6 |
| YOLOv5s | 49.1 |
| YOLOv8s | 36.2 |
| YOLO11s | 34.2 |

按三核并行估算，YOLOv5s 级模型可到约 100 FPS 以上；三路相机 30 fps 合计 90 帧/秒，**理论可满足**，但要留出预处理与后处理时间。若输入降到 320×320，算力余量更大。

**建议的替代方案**（需在报告中注明与原论文的差异）：

1. 反光检测改用 YOLOv5/v8 的 5 层特征版本替代 YOLOv3-5FL，工具链支持好、量化成熟；
2. RPN 只把特征提取与回归头放 NPU，候选框生成、NMS 用 C++ 在 CPU 实现（论文的 K-means 先验框可预先离线算好）；
3. 若 RPN 拆分后延迟仍不达标，可评估单阶段替代方案，但要在"复现报告"中明确标注偏离。

### 6.3 量化与精度

- INT8 需要校准集（现场图像 200–500 张）；
- 反光属于小目标，对量化误差敏感，建议优先尝试 **FP16**，或对反光分支单独做混合量化；
- 验收口径：与 PC 端 FP32 结果对比，平均 IoU 下降不超过 1–2 个百分点。

## 七、对外输出与系统集成

- **对外接口**：千兆以太网（TCP/UDP），输出检测结果 JSON、报警信号、可选缩略图；
- **现场总线**：Profinet / DeviceNet / EtherNet-IP 需通过认证网关模块接入，不在 RK3588 上自研协议栈（与 roadmap 的架构决策一致）；
- **分工**：RK3588 负责采集、推理、判定；工控机负责 HMI、配方、存档与报表；
- **实时性**：Linux 不适合硬实时，触发与 IO 由独立 MCU 负责，RK3588 只做计算（roadmap 已定）。

## 八、分阶段验证计划

| 阶段 | 内容 | 验证项 | 通过标准 |
| --- | --- | --- | --- |
| P5 台架 | RK3588 板 + 3 台 USB3 相机 + MVS Linux | 采集稳定性、三路同步、整链耗时 | 连续 8 h 无掉线；单帧 < 100 ms（先达标再优化） |
| P5.5 算法迁移 | 传统链路 C++ 化 + NPU 接入 | 精度对齐、延迟 | 与 PC 端结果一致；单帧 < 33 ms |
| P6 原型 | MIPI 模组 + 自研载板 | 带宽、触发时序、散热 | 三路 30 fps 无丢帧；温升可控 |
| P7 DVT | 整机联调 | 现场节拍、报警联动 | 与工控机版本功能对齐 |

## 九、风险与待确认清单

| # | 事项 | 影响 | 处理方式 |
| --- | --- | --- | --- |
| 1 | MVS Linux 的 USB3 内核模块能否在 RK3588 BSP 上编译 | 路线 A 是否成立 | 向海康机器人技术支持确认内核版本与源码提供方式；或改用 UVC 相机做台架 |
| 2 | 全局快门 MIPI 模组的供应与驱动 | 路线 B 选型 | 向模组厂索取 RK3588 适配说明；优先 OV9281 / AR0234 |
| 3 | RPN 在 NPU 上的拆分方案 | B1 能否落地 | 先做 CPU 版 proposal，评估延迟后再决定是否改网络 |
| 4 | INT8 量化对反光小目标的精度损失 | 反光检出率 | 用 FP16 或混合量化；建立量化前后对比流程 |
| 5 | 密封环形结构内的散热 | 长时间稳定性 | NPU 降频策略 + 铝基板/外壳导热；实测温升 |
| 6 | 三路相机与 LED 频闪的时序 | 成像一致性 | 同源硬件触发 + 曝光期间点亮 LED，示波器实测 |
| 7 | 交叉编译工具链与 BSP 版本锁定 | 开发效率 | 固定 SDK 版本，建立 Docker 构建环境 |

## 十、建议的下一步（可执行）

1. **买一块 RK3588 开发板**（如 Firefly / 创龙 / Radxa 的 8 GB 版本），先跑 MVS Linux aarch64，用现有 USB3 相机验证采集；
2. 同时**向海康机器人技术支持确认** Linux aarch64 SDK 的内核模块与 ARM 支持范围；
3. 在板上跑一遍现有算法（Python 版即可），测出真实耗时，作为优化基线；
4. 并行做**MIPI 全局快门模组**的选型与驱动预研；
5. 上述三项有结论后，再决定 P6 载板的相机接口形态。
